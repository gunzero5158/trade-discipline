# 持仓纪律工具 开发文档

版本 0.1 草案，2026-10-22。配套规则见同目录《交易纪律.md》，本文只讲怎么把那套纪律做成一个每天自动算的工具。

---

## 一、这个工具是干什么的

一句话：把《交易纪律》里每天收盘后要手工做的两步计算交给程序，人只负责看结论和执行。

纪律里最容易出错的不是规则本身，而是每天收盘后那两步手工活：算持仓以来的最高浮盈、算今天该把硬线挪到哪、看有没有收在均线下方。人会偷懒、会算错、会在该卖的时候找理由。程序不会。所以工具的核心就是每天收盘后自动算出每只持仓股明天的硬线价格和软线状态，给一句明确的结论。

**工具负责的事：**

- 记录持仓：代码、买入日期、买入价、股数、初始止损位、选定的均线、加仓记录。
- 每天收盘后拉 K 线，算最高浮盈、当前阶段、明天的硬线价格、软线是否触发。
- 给出每只股票明天的动作：继续持有、开盘卖出、卖三分之一落袋、等收盘确认。
- 新开仓计算器：输入买入价和止损位，算出仓位，校验单只上限和总风险闸。
- 加仓计算器：输入加仓价和关键位，算加仓量、合并硬线、做总账检查。
- 平仓归档：记出场价、触发的是硬线还是软线、折成 R 的盈亏。
- 月度统计：胜率、平均赢单 R 数、平均输单 R 数，自动从交易日志算。
- 云端存储，换浏览器、换手机数据不丢。

**工具不负责的事，要说清楚：**

- 不下单。硬线是盘中触发的，程序每天收盘后算一次，第二天盘中要你自己在券商软件里挂条件单或者盯盘。
- 不帮你看图。初始止损放在哪个支撑下方、这只股票用几日均线、加仓的关键位在哪，这是人的判断，程序只接收你填的数。
- 不选股、不给买入信号。它只管你已经决定买或已经持有的股票。

## 二、技术选型和为什么这么选

### 2.1 整体架构

```
浏览器（手机/电脑）
    │
    ▼
Next.js 应用，部署在 Vercel
    ├── 页面：今日看板 / 持仓详情 / 计算器 / 交易日志 / 设置
    ├── API：行情抓取、规则计算、数据读写
    └── 定时任务：每个交易日收盘后跑一次快照（Vercel Cron）
    │
    ▼
Turso 云数据库（SQLite 协议，免费额度足够）
```

一门语言（TypeScript），一个部署目标（Vercel），一个数据库（Turso）。没有第二套运行环境，没有跨语言的逻辑复制。

### 2.2 行情数据：复用 zenith-quant，不用 akshare

两条路都能走，选 zenith 那套的理由：

**zenith 已经解决了的问题。** zenith-quant 的 `src/lib/analysis/` 下面有一整套按市场分优先级的 K 线抓取：A 股走东方财富，失败切同花顺，再切腾讯，再切雅虎；港股美股类似。带熔断器（某个源连续失败两次就冷却五分钟）、带数据质量校验、带美股收盘后最后一根 K 线补全。这些坑都是踩过修过的，而且它就是在 Vercel 上跑的，说明从 Vercel 的海外节点访问这些国内数据源是通的。

**akshare 的问题。** akshare 是 Python 库，要用它就得多一套 Python 运行环境。FundSentinel 的做法是放在 GitHub Actions 里每天定时跑，再把结果写进数据库。这个模式对基金净值合适，因为净值一天只更新一次、晚上才出。但股票工具需要"打开页面就能看到最新计算"和"计算器实时算仓位"，这两样都要求计算逻辑在网页这一端，如果再在 Python 那端放一份同样的规则，两边就要同步维护，迟早对不上。另外 akshare 依赖抓取东财、新浪页面，接口变动时要等库更新，而 zenith 的抓取代码在自己手里，坏了当天就能修。

**具体搬哪些文件**，从 zenith-quant 的 `src/lib/analysis/` 原样复制，不改逻辑：

| 文件 | 作用 |
| --- | --- |
| marketDataPriority.ts | 按代码判断市场（A股/港股/美股/日股），给出数据源优先顺序 |
| eastmoneyHttp.ts、symbolConversion.ts | 东方财富 K 线接口和代码格式转换 |
| tencent.ts、tonghuashun.ts | 腾讯、同花顺备用源 |
| yahooChartCandles.ts | 雅虎图表接口，美股港股主力 |
| providerCircuitBreaker.ts | 多数据源顺序尝试加熔断 |
| ashareRealtime.ts | A 股盘中实时价，给"今天盘中是否已碰硬线"的提示用 |
| indicators.ts | 只用其中的 ATR，均线自己写一个简单移动平均 |
| symbolResolver.ts | 输入股票名字或代码时的联想搜索 |
| dataQuality.ts | K 线完整性检查 |

搬过来之后的封装只暴露两个函数给上层：按代码取最近 N 天日线，按代码取当前实时价。上层不关心数据从哪来。

### 2.3 数据库：Turso，访问码代替注册

**为什么是 Turso 而不是 Supabase。** 两个都免费够用。Supabase 的免费项目 7 天没人访问会被暂停，要去后台手动恢复；这个工具就是每天看一眼，出去一周回来发现打不开，很烦。Turso 没有这条。另外 zenith 的 commercial 分支里已经有 Drizzle 加 Turso 的连接和建表写法，可以直接借。用 Drizzle 做数据层的好处是以后想换成 Supabase 的 Postgres，改的是配置不是业务代码。

**为什么不做注册登录。** 这是自用工具。做邮箱注册要接邮件服务、做验证码、做密码找回，一堆和核心功能无关的活。改用访问码：第一次打开时生成一串 24 位随机码给你保存，之后所有数据都挂在这串码的哈希下面。换设备输一次就行。

代价是访问码丢了数据找不回来。两个兜底：页面上做一键导出 JSON；设置页提示你把访问码存进密码管理器。

### 2.4 定时任务

Vercel 的 Hobby 套餐允许每天跑一次 Cron。统一安排在北京时间 06:00 跑一次：这时 A 股港股看的是前一天收盘，美股刚收盘，三个市场在"开盘前知道该干什么"这个目标上都赶得上。

Cron 做的事：对每个持仓算一遍，把结果写进每日快照表。它不是计算的唯一入口，用户打开页面时也会实时算一遍，Cron 只是为了留痕和以后接推送。所以 Cron 挂了不影响使用，只影响历史记录。

## 三、规则计算的精确定义

这一节是程序的核心，每一条都对应《交易纪律》里的规则，这里把它写成程序能执行的样子。所有百分比按买入成本算，所有价格保留两位小数（港股美股按实际最小变动单位）。

### 3.1 一个持仓的输入

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| 代码 | 用户填 | A 股六位数字，港股 0700.HK，美股 AAPL |
| 买入日期、买入价、股数 | 用户填 | 支持多笔，首仓加加仓 |
| 初始止损位 | 用户填 | 按图放的那个价格，程序不替你算 |
| 软线均线 | 用户选 | 5/10/20/30 日，默认 20 日 |
| 软线确认天数 | 用户选 | 1 天或连续 2 天，默认 1 天 |
| 软线余量 | 自动 | 按近 20 日平均振幅定，见 3.5 |
| 关键位（加仓时） | 用户填 | 加仓那笔的止损参考位 |

### 3.2 每天算出来的东西

- 持仓以来最高价：取买入日期（含）之后所有日线的最高价的最大值。多笔的话按首仓日期算。
- 最高浮盈 = 最高价 ÷ 成本 − 1。成本用加权平均成本。
- 当前阶段：按最高浮盈落在哪个区间，见 3.3。
- 明天的硬线价格：按阶段算出来，再和昨天的硬线取大。硬线只升不降由这一步保证。
- 软线状态：今天收盘是否低于均线减余量；连续几天了；是否满足确认。
- 明天动作：见 3.6。

### 3.3 阶段与硬线

参数全部可在设置里改，这里是默认值。

| 阶段 | 进入条件（最高浮盈） | 硬线算法 | 软线均线 |
| --- | --- | --- | --- |
| 0 初始 | < 5% | 初始止损位 | 用户选的，默认 20 日 |
| 1 保本 | ≥ 5% | 成本 × (1 + 2%) | 同上 |
| 2 跟踪 | ≥ 10% | 成本 × (1 + 最高浮盈 × 50%) | 10 日 |
| 3 落袋 | ≥ 20% | 成本 × (1 + 最高浮盈 × 60%)，即回撤 40%；首次进入时提示卖出三分之一 | 10 日；加速段 5 日 |

阶段只升不降。因为最高浮盈本身只升不降，这一点自动成立。

**加速段判定**（阶段 3 内切换 5 日线的条件）：最近 3 个交易日每天收盘涨幅都超过近 20 日平均振幅，且收盘价高于 10 日线 8% 以上。满足则软线切 5 日，不满足回 10 日。这个判定是启发式的，第一版先这么做，验证期看效果。

### 3.4 多笔持仓的合并

加仓后：

- 成本 = 各笔金额总和 ÷ 总股数。
- 最高价仍从首仓日期起算。
- 阶段按合并成本算出的最高浮盈定。
- 硬线 = max(按阶段算出的硬线, 加仓那笔的止损位, 昨天的硬线)。三个取最大，这样加仓止损位高于阶段硬线时用加仓止损位，低于时不拉低。

### 3.5 软线

- 均线 = 收盘价的简单移动平均。
- 余量 = 近 20 日平均振幅（(最高 − 最低) ÷ 前收）× 0.5。振幅 2% 的股票余量 1%，振幅 5% 的股票余量 2.5%，和纪律文档里的说法对上。
- 今天触发 = 今天收盘 < 均线 × (1 − 余量)。
- 确认 = 连续触发天数 ≥ 用户设定的确认天数。

### 3.6 明天动作的判定顺序

从上到下，命中第一条就停：

1. 今天收盘已经低于明天硬线：明天开盘卖出全部。这种情况意味着今天盘中就该卖了，程序标红提示"硬线已穿，应已出场，请核对"。
2. 软线满足确认：明天开盘卖出全部。
3. 首次进入阶段 3：明天开盘卖出三分之一，剩余按硬线和软线继续。
4. 软线今天触发但未满确认天数：继续持有，提示"明日收盘再看一次"。
5. 其他：继续持有，显示硬线价格。

另外每条持仓都显示"硬线距今收盘的百分比"，让你一眼知道哪只离卖出最近。

### 3.7 开仓计算器

输入：总资金、买入价、止损位、单笔风险比例（默认 1%）。

- 每股亏损空间 = 买入价 − 止损位。
- 股数 = 总资金 × 风险比例 ÷ 每股亏损空间，向下取整到交易单位（A 股 100 股，港股按该股每手，美股 1 股）。
- 金额 = 股数 × 买入价。
- 校验一：金额 ÷ 总资金 > 25%，提示"仓位过重，止损太近，按图重新放止损或减仓位"，并给出按 25% 上限反算的股数。
- 校验二：加上现有持仓的未实现风险后总风险 > 5%，提示"总风险超闸，暂不开新仓"。现有持仓的未实现风险 = Σ max(0, (成本 − 硬线) × 股数)，硬线已在成本上方的算 0。
- 校验三（追涨）：止损距离 > 12% 或仓位 < 总资金 8%，提示"止损太远，性价比差，考虑放弃"。

### 3.8 加仓计算器

输入：选择已有持仓、加仓价、关键位。

- 加仓止损位 = 关键位 × (1 − 近 20 日平均振幅 × 0.5)。
- 风险额度 = 上一笔的一半：首仓 1%，第一次加仓 0.5%，第二次 0.25%。第三次拒绝。
- 加仓股数 = 总资金 × 风险额度 ÷ (加仓价 − 加仓止损位)，取整。
- 合并硬线 = max(当前硬线, 加仓止损位)。
- 总账 = 老仓在合并硬线处的盈亏 + 加仓在合并硬线处的亏损。总账 < −总资金 × 1% 时按比例缩减加仓股数直到满足。
- 校验：加仓后总金额不超过总资金 25%；加仓价距软线均线不超过 8%，否则提示"离均线太远，等于追高"。

### 3.9 平仓归档

平仓时填出场价、出场日期、触发原因（硬线/软线/落袋三分之一/手动）。程序算：

- 盈亏金额、盈亏比例。
- R 倍数 = 盈亏金额 ÷ 首仓风险金额（首仓股数 × (首仓价 − 初始止损位)）。
- 最高浮盈和实际落袋的差，用来看止盈规则吐回了多少。

部分平仓（卖三分之一）记为一条子记录，剩余仓位继续跟踪，全部平完后合成一笔完整交易。

### 3.10 月度统计

从交易日志算：笔数、胜率、平均赢单 R、平均输单 R、每笔期望 R、最大连亏次数、按触发原因分组的笔数。对照纪律文档第八节的三个检查点，自动给出提示：输单平均超过 1R 标"止损执行不严"，赢单平均不到 2R 标"止盈偏早"，胜率低于 40% 标"检查买点"。

## 四、数据模型

五张表，字段用中文说明，实际列名用英文。

**accounts 账户**：访问码哈希、创建时间、总资金、规则参数 JSON、最后访问时间。

**positions 持仓**：所属账户、代码、市场、名称、状态（持有/已平）、初始止损位、软线均线、确认天数、创建时间。

**lots 持仓明细**：所属持仓、类型（首仓/加仓）、日期、价格、股数、该笔止损位、该笔风险额度。

**snapshots 每日快照**：所属持仓、日期、收盘价、最高价、最高浮盈、阶段、硬线、均线值、软线是否触发、连续触发天数、明天动作、数据源。同一持仓同一天只有一条，重跑覆盖。

**trades 交易日志**：所属持仓、出场日期、出场价、股数、触发原因、盈亏金额、R 倍数、持仓最高浮盈、备注。

规则参数 JSON 的默认值就是 3.3、3.5、3.7、3.8 里的那些数字，放在账户级，改一处全部持仓生效。

## 五、页面

五个页面，手机优先，一屏能看完。

**今日看板**（首页）。一张表，一行一只持仓：代码名称、今收、成本、浮盈、阶段、明天硬线、距硬线百分比、软线状态、明天动作。按"距硬线百分比"从小到大排，最危险的在最上面。顶部一行显示总持仓风险占比和月度盈亏。动作是"卖出"的行标红，"等确认"标黄。

**持仓详情**。点进一只股票：K 线图叠加硬线、均线、买入点、加仓点（用 zenith 已有的 lightweight-charts）。下面是该持仓的每日快照历史表和各笔明细。有"加仓"和"平仓"两个按钮。

**计算器**。两个标签：开仓、加仓。按 3.7、3.8 做，算完可以一键转成持仓记录。

**交易日志**。已平仓列表加月度统计卡片。可导出 CSV。

**设置**。总资金、规则参数、访问码显示与复制、导出导入 JSON、清空。

## 六、开发里程碑

每个里程碑结束时要能独立跑起来用，不做半成品堆叠。

**M1 能算**（预计 2 到 3 个工作日）
搬行情模块、写规则引擎、单元测试覆盖 3.3 到 3.6 的全部分支和纪律文档里的算例。无界面，用脚本跑一只股票打印结果。验收：对纪律文档里 20 元买入那笔的所有算例，程序输出和文档数字一致。

**M2 能用**（2 到 3 个工作日）
Turso 建表、访问码、今日看板、持仓录入、持仓详情（先不画图）。验收：在手机和电脑上用同一访问码看到同一份持仓，每天打开能看到更新后的硬线。

**M3 能管**（2 个工作日）
开仓加仓计算器、平仓归档、交易日志、月度统计、导出导入。验收：走完一笔从开仓到加仓到部分落袋到平仓的完整流程，日志里 R 倍数正确。

**M4 能看**（1 到 2 个工作日）
K 线图叠加、Vercel Cron 快照、界面打磨。验收：Cron 连续跑三个交易日快照无缺失。

**之后可选**：推送提醒（Bark、企业微信、飞书，FundSentinel 里有现成分发器可以参考）；盘中实时价对照硬线的提醒；验证期结束后按统计结果调参数的辅助建议。

## 八、已知风险与待定

- **数据源稳定性**。东财等接口偶尔变动，zenith 的多源切换能扛大部分情况，但全挂的时候当天算不出来。页面要明确显示"行情获取失败，以下为上次快照"，不能静默显示旧数据当新的。
- **复权**。K 线用前复权。持仓期间碰到分红送股，成本和股数要手动调整，第一版不自动处理，在持仓详情页提供"手动校正成本和股数"的入口。
- **加速段判定**是拍的，验证期观察，不合适就改成手动切换。
- **港股每手股数**第一版让用户填，不自动查。
- **访问码是单点**。丢了就是丢了，靠导出备份兜底。如果以后要开放给别人用，这块要换成正经登录。
- **Vercel Hobby 的 Cron 限制**可能是每天一次且时间不精确（可能偏差一小时内）。所以不依赖 Cron 做实时判断，只做留痕。
